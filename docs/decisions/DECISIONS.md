# Decisions

Format: date, decision, reason. "TO DECIDE" means the reason is not recorded yet.

## 2026-09-29

1. **Project name is Treeps** (previously XCab, then SkyRides).
   Reason: the product was named Treeps by the owner.
2. **Stack: NestJS 12, Prisma 7.10, PostgreSQL, TypeScript.**
   Reason: existing project stack, kept as is.
3. **Prisma config is `prisma.config.ts` and points at the `prisma/` folder.**
   Reason: Prisma 7 rejects `url` in the schema file, and pointing at the folder is what makes models split across files (`schema.prisma`, `models/rider.prisma`) visible.
4. **Dev database `treeps_db` was emptied after a `pg_dump` backup (stored outside the repo). Old `User`, `OtpVerification` and `Role` were dropped and the init migration applied.**
   Reason: the old tables had no migration history, so `migrate dev` would have demanded a reset. The only data was one mock-login row.
5. **Never use `migrate reset`, `db push` or `--force`.**
   Reason: they can destroy data.
6. **Launch scope: Ranchi only; tiers MINI, SEDAN, XL.**
   Reason: TO DECIDE.
7. **The estimate API is built in layers, each switchable and done only when its check passes.**
   Reason: the layers fixed the owner's confusion about what to do step by step.
8. **Every variable is Input, Identity, Reference or Derived. Derived values are computed only by the server.**
   Reason: a client-sent price, distance, ETA, status or earnings could be forged; the server is the only trusted source.
9. **Money is stored as integer paise.**
   Reason: floating point rounding errors (for example 0.1 + 0.2) make totals disagree with breakdowns.
10. **Unknown request fields are rejected.**
    Reason: blocks a client sending a fake price or role.
11. **Every API and engine has a doc created from its template BEFORE its code is written.**
    Reason: this is a production app handling money and rider safety, so every API and engine must record why each field and rule exists; without that, later changes cannot be made safely.
12. **Line endings are LF, enforced by `.gitattributes` (`* text=auto eol=lf`).**
    Reason: Windows uses CRLF and Linux servers and CI use LF; mixed endings produce whole-file diffs and can break shell scripts on Linux.
13. **The agent tool folders (`.agents/`, `.windsurf/`, `.claude/skills/`) are no longer tracked.**
    Reason: they were the same 71 skill files stored three times (213 of 256 tracked files), and the `.claude` and `.windsurf` copies are links to `.agents`.
14. **`.claude/skills/` and `.claude/settings.local.json` are ignored, but a shared `.claude/settings.json` can still be committed.**
    Reason: skills and local settings are personal tooling, while shared settings are worth versioning.
15. **`skills-lock.json` stays tracked.**
    Reason: it records which skills are installed, so they can be reinstalled.
16. **`.env.example` was added, and the Firebase variable names are left out until F4 decides the auth flow.**
    Reason: it documents the required variables without secrets. The Firebase variables appear only in commented-out code.
17. **A valid request that breaks a business rule returns 422; invalid input returns 400.** This covers OUT_OF_SERVICE_AREA, PICKUP_DROP_TOO_CLOSE, TRIP_TOO_LONG and ROUTE_UNAVAILABLE.
    Reason: 400 means the request itself is malformed and must be corrected; 422 means the request is well formed but a business rule refuses it. Apps and logs can tell the two apart.
18. **PAYMENT_DUE and ACCOUNT_BANNED return 403.** 503 stays out of the registry until a real case appears (then a SERVICE_UNAVAILABLE row is added first).
    Reason: 402 is rarely used and handled inconsistently by clients, and the apps branch on the code anyway. PAYMENT_DUE and ACCOUNT_BANNED both mean this account cannot do this right now, so both use 403. 503 is not added until a real case exists.
19. **INVALID_INPUT carries `error.field` (the first invalid field) and an optional `error.details` list of `{ field, reason }` for every invalid field. `details` is omitted on all other codes.**
    Reason: The rider UI should highlight every invalid input at once instead of revealing one per retry.
20. **The error code is the contract; the message is an English fallback that apps may replace with their own localized text keyed on the code.**
    Reason: riders may read Hindi or English, and wording can change without breaking any app.
21. **A success with no result returns `data: null`.**
    Reason: every reply keeps one of the two shapes.
22. **Request id generation is part of F3.2, not F3.4.**
    Reason: The envelope carries requestId from the start, so generating it must exist in the same step; otherwise the field would ship empty.
23. **The request id is a UUID v4 generated by the server for every request (Node `crypto.randomUUID`). A client-sent id is ignored. It is returned in `requestId` and in the `X-Request-Id` header.**
    Reason: nobody can forge log entries.
24. **The error registry lives in `src/common/errors/`.**
    Reason: controllers never type a status or message, so every error has one status and one wording, kept in one place.
25. **`AppException` signature: `new AppException(code, { field?, details? })`. `details` is allowed only on INVALID_INPUT, and the constructor rejects it on any other code.**
    Reason: the code fixes the status and the message; `field` is per request.
26. **An unmapped 4xx HttpException becomes INVALID_INPUT 400 (`field` null). An unmapped 5xx and any non-HTTP error becomes INTERNAL_ERROR 500 with a generic message. Both are logged with the requestId. Dedicated codes for 405 and 413 stay TO DECIDE.**
    Reason: a client mistake such as an oversized body should not look like a server failure.
27. **Error logs contain the requestId, the error and its stack, and never request bodies or headers.**
    Reason: bodies and headers carry phone numbers and tokens.
28. **`setupApp(app)` (`src/common/setup-app.ts`) is the single place that registers global middleware, interceptors, filters and, later, pipes. `main.ts` and the tests both call it. F3.3 and F3.4 will add to it.**
    Reason: production and tests share identical wiring, so the tests prove what production does.
29. **The error-registry spec reads the table in `docs/standards/response-format.md` and fails if the code and the doc disagree.**
    Reason: the doc is the contract the apps rely on, so a silent difference between doc and code is a bug.
30. **One catch-all filter (`AllExceptionsFilter`) builds every error reply from the registry. No framework or error message is ever copied into a reply.**
    Reason: nothing internal can leak to a rider's phone.
31. **Log levels: a 4xx reply is logged as a warning with requestId, code and status (and `originalStatus` for an unmapped 4xx), without a stack. A 5xx or non-HTTP error is logged as an error with requestId, the error and its stack. The request URL, method, body and headers are never logged.**
    Reason: client mistakes do not need stack traces, and real failures do; bodies, headers and URLs can carry phone numbers and tokens (decision 27).
32. **A non-Nest error is treated as a 4xx only when its `status` (or `statusCode`) is 400 to 499 AND it has `expose === true` (body-parser errors do, for example 413 for an oversized body). Such an error becomes INVALID_INPUT 400. Any other non-Nest error stays INTERNAL_ERROR 500 and is logged as an error with its stack.**
    Reason: a client mistake such as an oversized body should not look like a server failure (decision 26), but an upstream provider's 4xx must never be shown to a rider as their mistake; it stays a 500 and is logged with its stack.
33. **The response interceptor always wraps what a handler returns as `{ success: true, data, requestId }`. It never unwraps or reads the returned value. `undefined` becomes `data: null`.**
    Reason: the shape of a reply must never depend on what a handler happens to return (the old code unwrapped `data.data` and read `data.message`).
34. **No 204 responses: an API with nothing to return replies 200 with `data: null`.**
    Reason: a 204 cannot carry a body, so the envelope would be lost.
35. **Controllers never use `@Res()` without the owner's approval.**
    Reason: it bypasses the envelope.
36. **The HTTP contract spec builds its list of error codes from `ERROR_REGISTRY`, so every new code is tested over real HTTP automatically.**
    Reason: a registry row cannot be added without its status, message and reply shape being checked end to end.
37. **`details[].reason` is one of 9 fixed codes (REQUIRED, UNKNOWN_FIELD, WRONG_TYPE, INVALID_FORMAT, OUT_OF_RANGE, NOT_ALLOWED, TOO_SHORT, TOO_LONG, INVALID_VALUE), never library text.**
    Reason: the apps localize on the codes, and library text can change or reveal internals.
38. **Unknown fields are rejected in the body, the query and the path, at any depth, including nested objects, list items and unknown query parameters.**
    Reason: it blocks a client sending a fake price, role or status (extends decision 10 to all three sources).
39. **No silent type coercion. Primitive-typed `@Param` and `@Query` parameters are banned; path, query and body values are read through DTO objects.**
    Reason: Nest's ValidationPipe silently converts primitive-typed parameters (`''` becomes 0, `'0x10'` becomes 16, any Boolean that is not `'true'` becomes false), which would let a changed value pass as what the client sent.
40. **Latitude, longitude and the other shared field types use our own strict validators, not `IsLatitude`, `IsLongitude` or `IsISO8601` directly.**
    Reason: `IsLatitude` accepts the string "12.5", and `IsISO8601` accepts time-zone offsets and date-only strings (checked against the installed class-validator).
41. **`details` is sorted A to Z by field name (plain code-unit order). `field` is the first entry of `details` that is not `$unknown`, or null if there is none.**
    Reason: the same request always gets the same reply, so tests and apps can rely on it. `field` lets the app highlight one input, and `$unknown` is not an input.
42. **An unknown field name is echoed only if it matches `^[A-Za-z_][A-Za-z0-9_.]{0,63}$`. All other unknown names collapse into ONE entry `{ "field": "$unknown", "reason": "UNKNOWN_FIELD" }`.**
    Reason: a name chosen by the client must not be reflected into a reply unless it looks like a normal field name.
43. **`details` holds at most 20 entries, applied after sorting. The request is rejected either way.**
    Reason: one request must not produce a huge reply.
44. **NODE_ENV is required at startup, one of development, test or production, with no default.**
    Reason: a missing value must stop startup instead of silently choosing a mode. The owner adds `NODE_ENV=development` to the local `.env`; the agent never edits `.env`.
45. **A test scans non-spec files under `src/` for the banned patterns: the built-in `Parse*Pipe`s and named extraction (`@Param('x')`, `@Query('x')`, `@Body('x')`). `src/auth/auth.controller.ts` is allowlisted until F4.**
    Reason: a rule kept only by review gets forgotten, and named body extraction skips the DTO rules entirely.
46. **A required field that is missing gives REQUIRED, never WRONG_TYPE. `null` on an optional field is WRONG_TYPE unless the API doc marks the field nullable. `IsOptional` is not used.**
    Reason: the app must be able to tell "absent" from "wrong type", and `IsOptional` would let `null` pass silently.
47. **Each API doc resolves the shared-type limits it uses before its code is written.**
    Reason: the docs-first rule (decision 11); code must not invent limits.
48. **A body that is missing, empty, an array, `null` or a bare string gives INVALID_INPUT with `field` null and `details` omitted.**
    Reason: there is no field to point at, so a `details` entry would invent one.
49. **Shared field types return a `FieldType` and become decorators only through `Required(...)` or `Optional(...)`. A property with neither is rejected as unknown.**
    Reason: `IsDefined` must be in required fields and absent from optional ones, and a field can then never forget to say which it is.
50. **Every shared-type limit that is TO DECIDE (money maximum, phone digit counts, page maximums, date range, text lengths, UUID versions) is a required parameter with no default.**
    Reason: code must not invent limits (decision 47); forgetting one is a compile error.
51. **Text length is counted in Unicode code points, so an emoji counts as 1.**
    Reason: it matches how users and Postgres count characters.
52. **The character U+0000 is rejected in text with INVALID_FORMAT.**
    Reason: Postgres cannot store it in text, and it would otherwise become a 500.
53. **`UtcDate` limits are functions (`min: () => Date`, `max: () => Date`), functions only.**
    Reason: relative ranges (for example "not in the past") can be expressed as well as fixed ones.
54. **Shared-type limit functions are checked once at definition time (both are functions, both return a valid Date, min is not after max), and a broken limit throws a `RangeError` naming the problem without printing any value.**
    Reason: a broken limit stops the server at startup instead of failing during a request.
55. **Clarifies decision 48: a body is unusable only if it is missing, `null`, an array, or a bare string, number or boolean. An empty object `{}` is a normal body and is validated by the DTO.**
    Reason: `{}` is well formed, and naming the missing required fields tells the app more than a blanket error.
56. **UTC dates with years 0000 to 0099 are rejected with INVALID_FORMAT.**
    Reason: JavaScript's `Date.UTC` reads those years as 1900 to 1999, so the value cannot round-trip; no real request is dated then, so refusing them costs nothing.
57. **The global pipe is `InputValidationPipe`: transform, whitelist, forbidNonWhitelisted, forbidUnknownValues, no implicit conversion, `validationError` target and value off, errors built by `toAppException`.**
    Reason: unknown fields are rejected (decisions 38, 39), nothing is converted silently, and errors can never carry the submitted value or library text (decisions 27, 37).
58. **The pipe refuses a missing, null, array or bare-value body as INVALID_INPUT with `field` null and no `details`. An empty object `{}` is validated normally.**
    Reason: Nest turns a missing body into `{}` and would report every required field as missing; JSON null and bare values are already refused by the body parser as malformed JSON, but a missing body, `text/plain` and `[]` reach the pipe (verified by running).
59. **Raw request access (`@Req()`, `@Request()`, `@Res()`, `@Response()`, `@Headers()`) is banned in non-spec files under `src/`, enforced by the banned-patterns test with a one-entry allowlist (`src/auth/auth.controller.ts`, "remove in F4"). The authenticated user will come from a guard plus a custom parameter decorator, decided in F4.**
    Reason: `@Req()`, `@Request()` and `@Headers()` hand out raw input that bypasses the DTO, and `@Res()` and `@Response()` bypass the response envelope.
60. **The route input check (`assertRouteInputs`) runs in `main.ts` and in a CI test over the real application modules (`real-routes.spec.ts`), not inside `setupApp`.**
    Reason: test apps use throwaway controllers with inline types, which the check would refuse; the CI test still fails on any real controller that breaks rule 14, and it proves the login is the only current violation.
61. **The server refuses to start (fails closed) if any `@Body()`, `@Query()` or `@Param()` has no DTO class with at least one rule, reads one named value, or has no decorator metadata. An allowlist entry that matches no route is also an error. The check runs after the modules are created and before `listen()`, so before `PrismaService.onModuleInit` and so before any database connection (rule 14).**
    Reason: Nest skips validation silently for an interface, an inline type, `unknown`, a primitive, and a class imported with `import type` (all recorded as `Object`, verified by running); a silent skip would let unvalidated input through.
62. **A top-level route DTO is instantiated at startup; an own property with a defined value (a silent default such as `page = 1`) or a constructor that throws stops the server. Declared fields that are undefined are fine. Nested DTOs are not checked.**
    Reason: a default set in a DTO satisfies "required" without the client sending anything, which contradicts rule 3 (no silent defaults); a DTO whose constructor throws cannot be validated at all.
63. **Vitest's `testTimeout` and `hookTimeout` are 15 seconds (`vitest.config.ts`), with no retries.**
    Reason: the heavier real-application spec runs in parallel and made three HTTP specs cross the 5 second default; a longer timeout removes the flakiness without hiding real failures; retries are not used because they hide real bugs.
64. **Environment validation is hand-written (`src/config/env.validation.ts`) with the fixed reason codes, and wired through `ConfigModule.forRoot({ validate })`. It reports every bad variable in one message that names the variable and the reason code, never the value. `DATABASE_URL` must start with `postgres://` or `postgresql://` and contain no control character; `NODE_ENV` is required with no default.**
    Reason: it reuses the fixed reason codes of decision 37 and cannot echo a secret; a default `NODE_ENV` would let a missing value silently choose a mode; `new URL()` alone accepts `postgresql:` with no host, so the prefix is checked first.
65. **The server checks the database before `listen()` (`src/config/database-check.ts`): connect, `SELECT 1`, close, within 5 seconds. Every failure gives one fixed message (`DatabaseCheckError`) with no cause and no input.**
    Reason: with the pg adapter Prisma connects lazily, so a wrong password or an unreachable host would otherwise appear only at the first request; pg has no default connect timeout and hangs on an unreachable host; the driver error text can contain the username, host or password.
66. **`PORT` rejects an empty value and leading zeros (`080`); it accepts plain digits from 1 to 65535 and is converted to a number explicitly.**
    Reason: `080` reads as octal in some tools and an empty `PORT=` is almost always a mistake, so both stop startup instead of being guessed.
67. **`main.ts` does not depend on Node's default unhandled-rejection behavior: every startup failure, and an `unhandledRejection` handler, go through `refuseToStart`, which prints one line and exits with code 1.**
    Reason: an invalid environment is a rejection raised outside `bootstrap()`; one operator flag (`--unhandled-rejections=warn`) would otherwise turn a refused start into a running server with a bad configuration.
68. **A startup failure prints its own message only if it is an `EnvConfigError`, a `DatabaseCheckError` or a `RouteInputsError`. Every other rejection value prints only `Startup failed. See server logs for details.`**
    Reason: a library message can contain a connection string, so it never reaches the console; our own three types build their messages from names, reason codes and constants only.
69. **The route input check throws its own `RouteInputsError` (message unchanged).**
    Reason: the check exists to tell the developer which controller and handler broke the rule, and its message contains no request data, so it is safe to print.
70. **The database check message says "could not run a test query ... (unreachable within 5 seconds, or refused the connection)".**
    Reason: one fixed text must be true for both a timeout and a refused login; it holds no value.
71. **The e2e test (`test/app.e2e-spec.ts`) calls `setupApp`, sets its own dummy `DATABASE_URL` and `NODE_ENV=test` before `AppModule` is imported, and replaces `PrismaService` with an empty stand-in.**
    Reason: it is the only test that boots the real `AppModule`, so it must test what production serves (the envelope, request id and error format), not the old raw reply; the dummy environment and stand-in stop it depending on a developer's `.env` or touching a database.
72. **Versioning uses Nest URI versioning with the default version `'1'`, not a global prefix `v1`.**
    Reason: a global prefix is one fixed string, so a v2 controller could not be served next to v1; URI versioning gives `/v1` now, `@Version('2')` later, and version-neutral routes.
73. **Versioning is applied inside `setupApp` (`enableApiVersioning`), and the throwaway-controller specs build their base URL with a test helper (`src/common/testing/base-url.ts`).**
    Reason: `setupApp` exists so production and tests share identical wiring; a separate call could be forgotten by the next entry point, and contract tests would then pass against routes production does not serve.
74. **A path with no version or an unknown version is the normal `NOT_FOUND` envelope, with no special rejection.**
    Reason: the route simply does not exist, so the existing unknown-route handling already answers it correctly and a new error code would add nothing.
75. **Version-neutral routes are reserved for `/health`.**
    Reason: a health check must keep the same address across versions so monitors never need updating; any other unversioned route would blur the versioning rule.
76. **Controllers never write the version in their path; a banned-patterns test enforces it.**
    Reason: the default version already adds the prefix, so a written `v1` would be served at `/v1/v1/...`.
77. **Login uses Firebase phone authentication, not our own OTP.**
    Reason: OTP SMS delivery in India needs DLT registration, and Firebase handles delivery and abuse limits, so far less security-critical code has to be written and maintained. The costs are a dependency on Google and SMS charges beyond the free tier. **Superseded by decision 84 (2Factor OTP).**
